# PixelRunner 3.0 产品方向与界面设计文档

版本：Draft 1
日期：2026-10-13
状态：产品设计讨论稿

## 1. 文档目的

本文档用于确定 PixelRunner 3.0 的产品边界、界面方向和实施顺序，为后续 UI 重构、体验优化和可靠性改进提供共同依据。

本版本只讨论产品和设计方向，不直接修改业务代码。后续开发应以本文档为基准，再根据实际验证结果迭代。

## 2. 核心判断

PixelRunner 2.9.1 已经完成了一个 Photoshop AI 插件应有的主要闭环：

```text
Photoshop 输入
  -> 捕获选区或文档
  -> 调用 RunningHub / 第三方 AI 能力
  -> 任务提交与状态追踪
  -> 结果下载
  -> Photoshop 回贴
  -> 对齐、校色和后期处理
```

同时，插件已经具备：

- RunningHub 应用解析和动态表单
- 应用、提示词、快捷入口和资料包管理
- 多任务并发与本地排队
- 生成式填充
- GRS、Gemini 等第三方能力
- Blend Match 像素对齐与校色
- 辉光、空间特效、镜头与后期
- 黑白观察层、中性灰、高低频等本地工具
- 授权、区域、诊断和发布相关基础设施

因此，3.0 的主要任务不应是继续无限扩大边界，而是把现有能力变成更清晰、更稳定、更容易上手的 Photoshop 工作台。

## 3. 3.0 产品定位

建议将 PixelRunner 3.0 定位为：

> **Photoshop 内更清晰、更稳定、更顺手的 AI 修图工作台。**

或者用于对外宣传：

> **像素起子 3.0：更快开始，更稳完成。**

这个定位包含三个关键词：

### 更清晰

用户打开插件后能迅速知道下一步做什么，不需要先理解 RunningHub、应用、模板、快捷入口和工具箱之间的关系。

### 更稳定

任务失败、网络中断、Photoshop 忙碌或回贴失败时，用户能看到明确原因，并能继续追踪、重试或重新回贴。

### 更顺手

高频动作更短，常用入口更近，复杂参数按需展开，熟练用户仍然可以使用完整控制。

## 4. 设计原则

### 4.1 现有架构优先

3.0 首要目标是体验升级，而不是技术栈迁移。以下内容默认保持：

- UXP 插件形态
- WebView 与 Host bridge 架构
- RunningHub 任务接口
- 现有第三方 Provider
- 现有 Photoshop 工具调用
- 现有状态持久化和资料包格式的兼容能力

UI 改造可以调整 HTML、CSS 和渲染组织，但不应为了视觉重做而破坏现有业务契约。

### 4.2 按用户任务组织，而不是按内部模块组织

用户的目标通常是：

```text
选择要做的事
  -> 准备图片
  -> 填写必要参数
  -> 运行
  -> 查看结果并继续处理
```

界面不应要求用户先理解“应用管理”“快捷入口”“资料包”“第三方支持”等内部概念。

### 4.3 渐进呈现

新手首先看到必要信息；高级选项、诊断信息和完整参数可以展开，但不能默认铺满面板。

### 4.4 不牺牲专业控制

简化默认路径不等于删除能力。所有现有高级功能都应保留，只是通过折叠、二级面板、搜索、最近使用和上下文入口呈现。

### 4.5 可逆和可恢复

涉及 Photoshop 修改或付费 AI 请求的操作，应尽量：

- 创建新图层或结果层
- 保留原始返图
- 显示执行前后的状态
- 失败后保留可继续操作的信息

## 5. 3.0 的范围

### 5.1 核心范围

1. 工作台 UI 信息架构重做。
2. 工具箱目录和分组重做。
3. 设置页分层和新手引导重做。
4. 动态表单的必填/常用/高级分层。
5. 任务卡片和结果操作的清晰化。
6. 失败状态、重试、继续追踪和重新回贴入口统一。
7. 最近使用、收藏和上下文入口增强。
8. 保持现有资料包、应用、模板、快捷入口和 Provider 兼容。

### 5.2 可选范围

以下功能可以在 3.0 期间视资源加入，但不应阻塞 UI 主线：

- 任务诊断摘要
- 结果 URL 保留
- 插件重载后的任务状态恢复
- 版本号单一来源
- 工具箱中少量本地图形算法增强

### 5.3 明确不纳入 3.0 核心

以下方向暂不作为 3.0 的必要条件：

- 完整 Copilot 或自由对话代理
- 本地 Qwen 等大模型前置安装
- 本地 ComfyUI 桥接
- ComfyUI 节点编辑器
- 桌面应用迁移
- 视频生成工作流
- 团队协作和云端工作流市场
- 大规模 Provider 扩张
- 为了 UI 而更换前端框架

这些方向可以保留为后续探索，但不能成为 3.0 的发布门槛。

## 6. 新版信息架构

当前的顶级导航“工作台 / 工具箱 / 设置”可以保留，降低用户迁移成本，但三个页面的内容组织需要改变。

### 6.1 工作台

工作台按以下顺序呈现：

```text
顶部状态
  - 当前文档
  - 当前图层 / 选区
  - API 与服务状态

快速开始
  - 最近使用
  - 收藏
  - 快捷入口
  - 添加应用

当前任务
  - 当前应用或快捷入口
  - 输入来源
  - 必填参数
  - 常用参数
  - 高级参数
  - 开始运行

后台任务
  - 运行中
  - 已完成
  - 失败与待处理

诊断信息
  - 默认折叠
```

#### 顶部状态区

顶部状态区不应占用过多空间，只需要回答三个问题：

1. 当前连接是否可用？
2. 当前 Photoshop 是否有可用输入？
3. 当前选中了什么？

建议使用紧凑状态条：

```text
RunningHub  已连接    当前文档  portrait.psd    当前选区  已存在
```

状态异常时，状态条直接提供恢复动作，例如“去设置”“重新读取”“捕获当前图像”。

#### 快速开始区

新用户首先看到的是可执行的入口，而不是完整应用列表：

- 最近使用
- 收藏
- 快捷入口
- 添加应用

应用选择器内部仍可保留完整搜索、编辑、删除和导入能力，但默认不把管理功能放在首屏。

#### 当前任务区

当前任务区是工作台的主体。动态表单继续由现有应用结构渲染，但视觉上分成三层：

- 必填参数：始终显示。
- 常用参数：默认显示或记住用户上次状态。
- 高级参数：折叠显示。

表单顶部应显示输入摘要：

```text
主图：当前选区  1280 × 960
参考图：未设置
蒙版：已设置
```

这样用户能在点击运行前确认图片是否填对。

#### 运行操作区

开始运行按钮应固定在当前任务区底部或面板底部，避免用户滚动到很长表单底部后找不到按钮。

按钮状态必须有明确原因：

- 未选择应用：选择应用后可运行
- 缺少必填字段：还差 1 项必填参数
- 未配置 API：去设置配置 API
- 可以运行：开始运行

#### 后台任务区

后台任务不应和运行表单混成一张卡片。任务卡片只展示：

- 应用名称
- 输入来源
- 当前状态
- 已用时间
- 主要操作

状态对应操作：

| 状态 | 主要操作 |
| --- | --- |
| 排队中 | 取消、查看参数 |
| 运行中 | 取消、查看详情 |
| 下载中 | 查看详情 |
| 回贴中 | 查看详情 |
| 已完成 | 回贴、重新回贴、打开结果 |
| 失败 | 重试、继续追踪、复制诊断 |

原始运行日志应默认折叠，不要让普通用户在首屏看到大量技术文本。

### 6.2 工具箱

工具箱从“大卡片介绍”调整为“动作目录”。建议分成四组：

#### 修图辅助

- 黑白观察层
- 中性灰图层
- 高低频
- 饱和度观察层

#### AI 返图处理

- 对齐与校色
- 创成式填充
- 结果回贴相关操作

#### 光效与后期

- 辉光
- 空间特效
- 镜头与后期

#### Photoshop 操作

- 高斯模糊
- 锐化
- 高反差保留
- 内容识别填充
- 选择并遮住
- 盖印图层

每个工具使用紧凑的行项目：

```text
工具名称       一句话用途                  [打开]
```

高级工具可以显示“需要选区”“需要当前图层”等前置条件，避免用户点击后才看到错误。

建议增加：

- 最近使用
- 收藏工具
- 工具搜索
- 按使用对象筛选：当前图层 / 当前选区 / 整个文档

辉光、空间特效、镜头与后期仍然可以使用独立预览弹窗，不需要把预览能力塞回工具箱首页。

### 6.3 设置

设置页按“是否影响首次运行”分层：

#### 必要设置

- RunningHub 区域
- API Key
- API 档案
- 保存设置

#### 资料与资产

- 当前资料包
- 导入资料包
- 导出资料包
- 应用、模板和快捷入口说明

#### 第三方服务

- GRS
- Gemini / NewAPI
- 其他已支持渠道

#### 授权与设备

- 激活状态
- 设备信息
- 授权操作

#### 高级设置

- 并发
- 本地排队
- 主题
- 应用选择器布局
- 诊断和日志选项

首次打开设置时只展开必要设置，其余内容使用 `<details>` 或二级面板。

## 7. 新手引导设计

不建议增加一套长教程。采用“状态驱动的轻量检查清单”：

```text
开始使用像素起子
✓ 已打开 Photoshop 文档
○ 配置 RunningHub API
○ 添加一个应用
○ 捕获一次图像
○ 完成一次测试运行
```

每一项都能直接跳转到对应动作。完成后自动隐藏，只保留一个“查看入门检查清单”的入口。

### 新手状态判断

| 状态 | 工作台主提示 |
| --- | --- |
| 无文档 | 请先在 Photoshop 打开一份文档 |
| 无 API | 去设置保存 RunningHub API Key |
| 无应用 | 添加一个 RunningHub 应用或导入资料包 |
| 有应用无输入 | 捕获当前选区或文档 |
| 可运行 | 已准备好，可以开始运行 |
| 有失败任务 | 先处理失败任务，或继续开始新的任务 |

## 8. UI 视觉方向

### 8.1 工作台密度

插件面板空间有限，应优先使用：

- 紧凑行布局
- 清晰分组标题
- 单层卡片
- 固定操作区
- 折叠高级内容

减少：

- 大面积说明文字
- 首屏大卡片
- 重复的版本和支持入口
- 普通用户不需要的技术状态

### 8.2 层级

页面层级建议稳定为：

```text
页面标题
  -> 区域标题
    -> 工具 / 表单行
      -> 辅助说明
```

避免多个同等级的标题、状态芯片和描述同时争夺注意力。

### 8.3 操作按钮

- 页面主操作使用一个明确的主按钮。
- 次要操作使用轻量按钮或图标按钮。
- 删除、覆盖、付费提交等高风险动作需要明确文本和确认。
- 图标按钮必须带 tooltip 或 aria-label。
- 同一屏不要出现多个视觉重量相同的主按钮。

### 8.4 状态颜色

状态颜色必须具有一致含义：

- 蓝色：信息、准备中
- 绿色：完成、可用
- 黄色：等待、需要注意
- 红色：失败、不可用
- 灰色：未配置、未运行

不能仅使用颜色表达状态，应同时显示文字。

## 9. 任务与错误体验

3.0 的可靠性重点不是增加更多日志，而是让错误能够指导下一步。

### 错误分类

#### 配置错误

例如 API Key 缺失、区域不匹配、应用 ID 无效。

显示：

```text
未配置 RunningHub API Key
[去设置]
```

#### 输入错误

例如缺少图片、选区为空、尺寸不符合应用要求。

显示：

```text
当前应用需要一张主图
[捕获当前选区] [捕获整个文档]
```

#### 云端任务错误

保留 taskId、详情链接、原始错误摘要，并提供：

- 重试提交
- 继续追踪
- 打开任务详情
- 复制脱敏诊断

#### 回贴错误

即使 Photoshop 回贴失败，也必须保留 outputUrl 或本地结果缓存，并提供：

- 重新回贴
- 另存结果
- 打开结果链接

## 10. 资料包与资产兼容

3.0 不改变用户对资料包的基本认知。资料包仍然保存：

- 应用
- 提示词分类
- 提示词预设
- 快捷入口

UI 上需要明确区分：

- 保存设置：保存 API 和插件偏好
- 保存应用：保存一个 RunningHub 应用配置
- 保存模板：保存 Prompt 和参数预设
- 导出资料包：备份多个资产

导入资料包时，应在预览中显示：

```text
将导入：
应用 12 个
提示词模板 28 个
快捷入口 6 个
发现同名项目 3 个
```

## 11. 实施路线

### 阶段一：信息架构原型

目标：确认布局方向，不改变业务逻辑。

- 重排 `app.html` 页面结构
- 建立工作台、工具箱、设置的新版视觉骨架
- 保留所有现有 DOM id 或建立兼容映射
- 不改 Host bridge 和任务协议
- 使用现有假数据或真实状态验证布局

验收：

- 新用户能在不看教程的情况下找到添加应用、捕获输入和开始运行
- 熟练用户能在两次点击内打开最近使用的应用或工具
- 现有弹窗和任务逻辑仍能正常打开

### 阶段二：工作台交互优化

- 最近使用和收藏入口前置
- 输入摘要显示
- 必填/常用/高级字段分层
- 底部固定运行操作区
- 任务卡片动作统一
- 日志默认折叠

### 阶段三：工具箱重排

- 按用途重新分组
- 工具搜索和最近使用
- 前置条件提示
- 统一打开 / 运行按钮行为
- 保留现有独立预览弹窗

### 阶段四：设置和新手引导

- 设置分层
- 添加检查清单
- 统一状态和错误跳转
- 补充资料包导入预览

### 阶段五：可靠性补强

- 结果 URL 保留
- 重新回贴
- 失败任务继续追踪
- 诊断摘要
- 任务状态恢复
- 版本号单一来源

## 12. 工程约束

### 必须保持

- 现有业务模块和 Provider 接口可继续使用。
- 现有资料包旧版本可以导入。
- 现有快捷入口和模板数据不丢失。
- 现有 Photoshop 操作仍通过 Host 层执行。
- UI 重构不能绕过授权校验。

### 允许调整

- HTML 结构和 CSS。
- 页面区域的排列顺序。
- 渲染函数输出的包装结构。
- UI 状态提示和折叠状态。
- 应用选择器的展示排序。

### 暂不建议

- 直接迁移 React/Vue/Svelte。
- 重写所有 WebView 状态管理。
- 同时重构 Provider、Photoshop service 和 UI。
- 为了新 UI 删除旧 DOM id 后再大范围修复事件绑定。

## 13. 3.0 成功指标

### 新手上手

- 首次打开后能找到下一步操作。
- 从打开插件到完成第一次测试运行的步骤减少。
- API、应用、输入和运行状态不再需要用户自行猜测。

### 熟练用户效率

- 最近使用和快捷入口能快速进入。
- 常用工具不需要滚动浏览长说明卡片。
- 高级字段不会干扰常规运行。

### 可靠性

- 失败任务都有明确恢复路径。
- 回贴失败不会丢失结果。
- 插件重载后重要任务状态尽量可恢复。

### 兼容性

- 旧资料包可导入。
- 现有 Provider 和应用表单继续工作。
- 现有工具弹窗和 Photoshop 操作保持可用。

## 14. 最终产品判断

PixelRunner 3.0 不需要通过无限增加功能来证明是一次大版本更新。

更合理的方向是：

```text
2.9.1：功能已经丰富，但入口和层级较多
3.0：保留能力，重新组织体验，降低理解和操作成本
```

3.0 的完成标准不是“支持了多少新平台”，而是用户打开插件后可以更快开始，运行过程中更少迷惑，失败后更容易恢复，完成后更愿意继续使用。

后续所有新增能力都应先回答一个问题：

> 它是否让现有 Photoshop AI 修图流程更清晰、更稳定或更顺手？

如果不能明确回答，就不应为了版本号把它加入 3.0。
